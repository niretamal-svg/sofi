INFORME TÉCNICO
Módulo de Publicación en Portales de Empleo
API REST · Endpoints Internos · Integraciones Externas · Consideraciones Técnicas
1. Introducción
SOFI (Sistema de Apoyo al Reclutamiento) es una plataforma SaaS diseñada para automatizar y centralizar el proceso de publicación de vacantes laborales en múltiples portales de empleo. Este informe técnico describe la arquitectura de la API REST, los endpoints desarrollados internamente en FastAPI, las integraciones con servicios externos y las consideraciones técnicas críticas para el desarrollo, despliegue y mantenimiento del módulo de Publicación en Portales de Empleo.
El módulo cubre todo el ciclo de vida de una publicación: desde la autenticación del reclutador, la creación y gestión de vacantes, la generación de perfiles de anuncio (manual o asistida por IA), la selección de portales de empleo, hasta la gestión de pagos y el seguimiento del estado de cada publicación en cada portal externo.
1.1 Alcance del Sistema
El módulo opera sobre la base de datos MongoDB denominada sofi_db y expone una API REST con base URL:
Todos los endpoints requieren autenticación mediante Bearer JWT en el header Authorization, a excepción del proceso de login. Las respuestas siguen una estructura estándar con campo success, data y meta para paginación.
1.2 Módulos Funcionales
El sistema se organiza en seis módulos funcionales principales, cada uno con su conjunto de endpoints:
Autenticación: gestión de sesiones JWT con login y refresco de tokens.
Vacantes: CRUD completo del ciclo de vida de vacantes laborales.
Perfiles de Cargo: perfiles de anuncio reutilizables con soporte de IA generativa.
Portales de Empleo: catálogo de portales disponibles con información de cobertura y costos.
Campañas de Publicación: flujo central multi-portal que orquesta la publicación.
Pagos: procesamiento de transacciones para portales de costo con integración a gateway externo.
1.3 Flujo General del Sistema
El flujo operativo comienza con el login del reclutador. Una vez autenticado, el sistema valida sus credenciales y le presenta el catálogo de vacantes. El reclutador busca o crea una vacante, le asigna un código único, y procede a crear un perfil de cargo (manualmente o mediante la IA generativa de SOFI). Luego selecciona los portales de empleo donde publicar, visualiza una previsualización del anuncio, y si algún portal tiene costo, se inicia el proceso de pago. Una vez confirmado el pago (o si todos los portales son gratuitos), la campaña pasa a estado de publicación activa.
2. Endpoints Internos — Desarrollo en FastAPI
Todos los endpoints listados a continuación son desarrollados e implementados internamente en el backend FastAPI de SOFI. Se comunican directamente con la base de datos MongoDB (sofi_db) y aplican las reglas de negocio del sistema.
2.1 Autenticación
Gestiona el ciclo de vida de las sesiones de usuario. El access_token tiene una vigencia de 8 horas; el refresh_token persiste 30 días y debe almacenarse en una cookie httpOnly.
Cuerpo de la solicitud: email (string, requerido) y password (string, requerido, mínimo 8 caracteres). La respuesta exitosa (200) retorna access_token, refresh_token y los datos básicos del usuario (id, nombre, email, rol). Implementa bloqueo temporal de 15 minutos tras intentos fallidos reiterados (código ERR_TOO_MANY_ATTEMPTS).
Recibe el refresh_token en el body y retorna un nuevo access_token. Invalida el token si la cuenta fue desactivada después de su emisión.
2.2 Gestión de Vacantes
Endpoints para el CRUD completo del ciclo de vida de vacantes. Las vacantes poseen estados controlados (borrador, vigente, pausada, cerrada) y un código numérico secuencial auto-incrementado asignado al momento de creación.
Soporta filtros por empresa_id, estado, categoria_id, vigente y búsqueda de texto libre (q) sobre nombre y descripción usando el índice de texto de MongoDB. Ordenamiento configurable por createdAt, codigo o nombre. La respuesta incluye datos resumidos de cada vacante con referencias a empresa y categoría.
Campos requeridos: nombre (3–200 caracteres), empresa_id, categoria_id y estado. Verifica la existencia y estado activo de empresa y categoría antes de persistir. El código numérico es generado automáticamente por el sistema. Retorna 201 con el id y código asignados.
Retorna el documento completo de la vacante incluyendo datos expandidos de empresa (id, nombre, logo_url), categoría (id, nombre, slug), reclutador asignado, lista de preguntas asociadas y resumen de campañas de publicación vinculadas.
Todos los campos del body son opcionales (actualización parcial). Controla las transiciones de estado válidas: no se puede transicionar directamente desde estado 'cerrada' a otro estado (ERR_INVALID_STATE). Retorna el documento completo actualizado.
2.3 Perfiles de Cargo
Gestión de perfiles de anuncio reutilizables. Un perfil define el contenido del anuncio que verá el candidato en el portal: título, descripción, requisitos, beneficios y condiciones laborales. Los perfiles pueden crearse manualmente o generarse mediante el motor de IA integrado.
Soporta filtros por empresa_id, categoria_id y búsqueda de texto (q). Ordenamiento por popularidad (-veces_usado) o fecha de creación (-createdAt). El campo veces_usado permite identificar los perfiles más utilizados para reutilización eficiente.
Campos requeridos: nombre_perfil, titulo_anuncio (máx 200 caracteres), empresa_id, categoria_id, tipo_jornada y descripcion (máx 8000 caracteres). Campos opcionales para salario (salario_min, salario_max con validación salario_max ≥ salario_min), moneda (ISO 4217), requisitos, beneficios y configuración de IA (ia_chips, tono).
Este endpoint invoca al servicio de IA interno para generar automáticamente el contenido del anuncio. Recibe una descripcion_libre en lenguaje natural (mínimo 20 caracteres, máximo 1000) y retorna una propuesta completa con titulo_anuncio, descripcion, requisitos, beneficios, tipo_jornada, ia_chips identificadas y sugerencias adicionales. El perfil generado NO se persiste automáticamente; el usuario debe confirmarlo y guardarlo usando POST /perfiles.
2.4 Portales de Empleo
Retorna el catálogo maestro de portales de empleo disponibles. Soporta filtros por paises (lista separada por comas, ISO 3166-1 alpha-2), modelo_empresa (gratis, pago, freemium, cpc), tipo (bolsa, agregador, red_social, gobierno, clasificados) y api_disponible. La respuesta incluye costo_base y moneda para que el reclutador pueda estimar el costo de la campaña antes de iniciarla.
2.5 Campañas de Publicación
Flujo central del módulo. Una campaña asocia una vacante con un perfil de cargo y un conjunto de portales seleccionados. El estado de la campaña (y de cada portal dentro de ella) es gestionado de forma independiente.
Al crear la campaña, el sistema evalúa automáticamente si los portales seleccionados tienen costo. Si hay portales de pago, el estado inicial de la campaña es 'pendiente_pago'; si todos son gratuitos, pasa directamente a 'publicando'. Calcula el costo_total estimado sumando los costos de los portales de pago. Valida que la vacante no esté en estado 'cerrada'.
Incluye el estado detallado de cada portal individual: pendiente, publicando, publicado, error o pendiente_pago. Para los portales con API disponible, registra url_publicacion, id_externo asignado por el portal y número de intentos. También incluye información del pago asociado si existe.
Permite filtrar por empresa_id, vacante_id y estado de la campaña. Retorna listado paginado con resumen de cada campaña.
Acepta un motivo opcional (máx 500 caracteres) que se guarda en el campo notas. No se puede cancelar una campaña ya cancelada (ERR_ALREADY_CANCELLED) ni una campaña en estado 'publicada' que tenga portales activos de pago (ERR_CANNOT_CANCEL).
2.6 Pagos
Gestión de transacciones de pago para campañas con portales de costo. El procesamiento es asíncrono: la API retorna inmediatamente un estado 'procesando' y actualiza el estado del pago y la campaña cuando el gateway externo confirma o rechaza la transacción.
Métodos aceptados: tarjeta (requiere token_pago tokenizado del proveedor), transferencia y credito_sofi. La respuesta (202) incluye un redirect_url para flujos que requieren 3DS u OTP. Errores específicos para campañas sin costo (ERR_CAMPANA_SIN_COSTO) y pagos duplicados (ERR_ALREADY_PAID).
Incluye el estado actual del pago (pendiente, procesando, completado, fallido, reembolsado), referencia externa del proveedor, y desglose de costos por portal para auditoría.
3. Integración con APIs Externas
SOFI integra tres categorías de servicios externos que son esenciales para el funcionamiento del módulo de publicación: portales de empleo con API disponible, un gateway de pagos y un servicio de IA generativa. Estas integraciones están desacopladas del núcleo interno y se gestionan mediante referencias seguras a secrets en vault.
3.1 Portales de Empleo con API Disponible
Dentro del catálogo de portales, aquellos con el campo api_disponible: true cuentan con integración directa. Los campos api_endpoint y api_key_ref (referencia al secret en vault, nunca la clave en texto plano) habilitan al sistema a publicar automáticamente sin intervención manual.
El subdocumento publicacion_portal (embebido en publicaciones_campana.portales[]) registra el ciclo de vida de cada publicación individual en portales externos, incluyendo:
url_publicacion: URL del anuncio publicado en el portal externo (disponible tras publicación exitosa).
id_externo: ID asignado por el portal externo para referencia y gestión posterior.
intentos (Int32): contador de intentos de publicación para manejo de reintentos.
ultimo_intento (Date): timestamp del último intento, para backoff exponencial.
error_msg (String): mensaje de error del último intento fallido para diagnóstico.
publicado_en (Date): timestamp de publicación exitosa confirmada por el portal.
Para portales sin API disponible, la publicación es manual: el sistema notifica al reclutador las instrucciones específicas del portal y registra la publicación una vez que el reclutador confirma haberla realizado.
3.2 Gateway de Pagos
La integración con el proveedor de pagos externo es asíncrona. SOFI actúa como orquestador: recibe la solicitud de pago del reclutador, la reenvía al gateway y espera la confirmación mediante webhook o polling.
Los métodos de pago soportados son: tarjeta (requiere token tokenizado del proveedor, compatible con flujos 3DS), transferencia bancaria y crédito_sofi (saldo interno). El campo desglose en la colección pagos permite auditar el monto cobrado por cada portal individual.
Códigos de error específicos de la integración: ERR_PAYMENT_DECLINED (HTTP 402) cuando el gateway rechaza la transacción, y ERR_PAYMENT_GATEWAY (HTTP 503) cuando el servicio externo no está disponible. En ambos casos el sistema registra el error y permite reintentar sin crear un duplicado de pago.
3.3 Servicio de IA Generativa
El endpoint POST /perfiles/ia/generar actúa como proxy hacia el servicio de IA interno o externo de SOFI. Este servicio recibe el contexto de la vacante y genera contenido profesional para el anuncio de empleo.
El servicio retorna una propuesta completa no persistida: titulo_anuncio, descripcion, requisitos, beneficios, tipo_jornada sugerido, ia_chips identificadas y un array de sugerencias adicionales. El usuario puede editar el resultado antes de guardar con POST /perfiles. La bandera generado_por_ia queda registrada en el perfil para trazabilidad.
Si el servicio no está disponible, retorna ERR_IA_UNAVAILABLE (HTTP 503), permitiendo al reclutador continuar el flujo con creación manual del perfil.
4. Consideraciones Técnicas Fundamentales
4.1 Autenticación y Seguridad
Todos los endpoints (excepto los de autenticación) requieren un Bearer JWT válido. La arquitectura de seguridad implementa los siguientes mecanismos:
JWT de acceso con expiración de 8 horas y refresh token con vida de 30 días almacenado en cookie httpOnly.
Control de acceso basado en roles: admin, reclutador y viewer con permisos diferenciados por recurso y empresa.
Protección contra fuerza bruta: bloqueo temporal de 15 minutos tras intentos de login fallidos reiterados (ERR_TOO_MANY_ATTEMPTS, HTTP 429).
API keys de portales externos almacenadas exclusivamente mediante referencias a secrets en vault; nunca en base de datos ni código fuente.
Tokens de tarjeta tokenizados por el proveedor de pagos; SOFI nunca manipula datos de tarjeta en texto plano (PCI-DSS compliance).
4.2 Modelo de Datos MongoDB
El diseño del modelo de datos prioriza la consistencia referencial mediante ObjectIds y la eficiencia de consulta mediante índices estratégicos. Consideraciones clave:
Auto-incremento de código en vacantes: implementar con operación atómica findAndModify sobre un contador dedicado para garantizar unicidad bajo concurrencia.
Desnormalización controlada: nombre_portal en subdocumento publicacion_portal se almacena redundantemente para evitar joins costosos en consultas frecuentes de estado.
TTL index: el índice { estado: 1, fecha_expiracion: 1 } en publicaciones_campana es compatible con jobs de expiración automática de campañas.
Índice de texto: { nombre: 'text', descripcion: 'text' } en vacantes debe crearse en horario de bajo tráfico. Evaluar Atlas Search para entornos de alta concurrencia.
Índices únicos críticos: email en usuarios, codigo en vacantes, slug en portales y categorias, campana_id en pagos.

4.4 Procesamiento Asíncrono
Las publicaciones en portales externos y el procesamiento de pagos son operaciones asíncronas. El sistema debe implementar:
Worker/queue para procesar publicaciones en portales con API: enviar el anuncio, esperar confirmación y actualizar el estado del subdocumento publicacion_portal.
Manejo de reintentos con backoff exponencial: los campos intentos y ultimo_intento en publicacion_portal soportan esta lógica. Definir máximo de reintentos por portal.
Webhook receiver para confirmaciones del gateway de pagos: debe validar la firma del payload antes de actualizar el estado del pago y desencadenar las publicaciones pendientes.
Jobs de expiración automática: basados en el índice { estado, fecha_expiracion } para cerrar campañas vencidas.
4.5 Manejo de Errores y Códigos HTTP
La API implementa un catálogo estandarizado de 30+ códigos de error internos que garantizan respuestas consistentes y manejables por el cliente. Principios clave:
Todos los errores siguen la estructura: { success: false, error: { code, message, details } }.
El campo details en ERR_VALIDATION contiene un array de { field, message } para validación campo a campo.
Los errores de servicio externo (ERR_IA_UNAVAILABLE, ERR_PAYMENT_GATEWAY) retornan HTTP 503 indicando reintento.
ERR_INTERNAL (HTTP 500) incluye trace_id para correlación con los logs del servidor.
HTTP 202 (Accepted) para operaciones asíncronas (inicio de pago) diferencia procesamiento en curso de éxito inmediato.
4.6 Paginación y Rendimiento
Todos los endpoints de listado implementan paginación estándar con los parámetros page (base 1) y limit (máximo 100). La respuesta siempre incluye meta.total, meta.page, meta.limit y meta.pages. Consideraciones de rendimiento:
Los índices compuestos (empresa_id + estado, activo + paises + modelo_empresa) están diseñados para los filtros de consulta más frecuentes.
El índice { veces_usado: -1 } en perfiles_cargo permite ordenar eficientemente por popularidad sin sort en memoria.
El índice { createdAt: -1 } en pagos optimiza las consultas de historial más recientes primero.
Las búsquedas de texto libre en vacantes usan el índice de texto de MongoDB; para alta concurrencia, migrar a Atlas Search o Elasticsearch.
4.7 Cobertura Geográfica y Multimoneda
El sistema está diseñado para operar en múltiples países latinoamericanos (MX, GT, HN, SV, NI, US). Esto implica:
Códigos de país en formato ISO 3166-1 alpha-2 en todos los documentos relevantes (empresas, portales, campañas).
Monedas en formato ISO 4217 (MXN, GTQ, HNL, USD, etc.) con validación en API (ERR_INVALID_MONEDA).
Cada portal puede tener su propia moneda (moneda_portal en publicacion_portal); la campaña consolida el costo_total en una moneda unificada.
El desglose en pagos registra el monto de cada portal en su moneda original para auditoría y conciliación contable.

4.2  Estándares  Técnicos  de  Alloxentric  Todo  el  desarrollo  debe  adherirse  a  los  estándares  técnicos  transversales  establecidos  por  
Alloxentric:
  
Multi-Tenancy 
Aislamiento  lógico  de  datos  por  cliente  (client_id)  en  base  de  datos  y  APIs.  El  catálogo  de  portales  de  Sofi-Publ  es  particionado  por  empresa  cliente.   
Feature  Gating 
Las  funcionalidades  del  módulo  estarán  protegidas  por  feature_flags  vinculados  al  perfil  comercial  del  cliente.  El  frontend  reacciona  dinámicamente  al  perfil  comercial  obtenido  en  autenticación.   
RBAC  Granular 
Control  de  acceso  basado  en  roles  dentro  de  cada  organización  cliente.  Los  tokens  JWT  transportan  claims  de  permisos  para  decisiones  de  autorización  en  backend  y  frontend.   
API-First 
Toda  interacción  con  el  módulo  (registro  de  portales,  activación  de  agentes,  consulta  de  estado  de  publicaciones)  se  expone  a  través  de  endpoints  REST  documentados.   
Auditoría  de  Logs 
Cada  acción  del  sistema  (publicación  exitosa,  falla,  activación/desactivación  de  portal)  genera  un  log  estructurado  con  las  5  dimensiones:  Quién,  Qué,  Cuándo,  Desde  dónde  y  Resultado.   
i18n  y  Accesibilidad 
La  interfaz  de  administración  debe  soportar  internacionalización  (ES/EN  mínimo)  y  cumplir  estándares  de  accesibilidad  visual  incluyendo  soporte  de  tema  claro/oscuro.
